# ADR 0024: Separate shared family trackers with membership permissions

## Status

Accepted October 7, 2026. Updates ADRs 0001, 0003–0006, 0017, 0020, 0021, and 0023. Supersedes their single-dataset assumptions for shared trackers while preserving the personal tracker and its optional sync. Implementation and validation evidence belong in the tracker development runbook; this decision does not claim deployment or paired-device acceptance.

## Context

Each family member needs a private personal tracker plus access to a separate common dataset. Two parents may have equal admin control while a child records income and expenses without changing budgets or categories. Existing local persistence, opt-in personal sync, immutable mutation retries, and delayed Wear OS recordings must remain safe when multiple datasets coexist.

## Decision

- Keep one canonical personal cloud dataset per Cognito subject and optional personal sync. Allow multiple separately named shared datasets per subject through memberships. A shared tracker starts empty with protected system categories and chosen currency preferences; creation/joining includes an explicit cloud-sharing notice and never uploads personal records.
- Roles are `admin` and `member`. Both read all financial data and create transactions. Members edit/delete only their own transactions; admins manage all transactions, budgets, categories, currencies, tracker name, memberships, invitations, and archive/restore. All admins have equal authority. The last admin cannot leave, be removed, or be demoted. Membership administration requires connectivity.
- Display account emails in membership and transaction attribution. Authorize by immutable Cognito `sub`, not email. Stamp creator metadata server-side and retain it through edits and member removal. Local shared creates may carry tentative creator metadata for display; the server remains authoritative. Creator metadata is not part of financial mutation payloads or hashes and never causes a metadata-only outbox entry.
- Retain `datasets.owner_subject` uniqueness for personal compatibility and allow null ownership for shared datasets. Shared permissions come only from memberships. Add forward SQL migrations, preserving all existing IDs, history, acknowledgment hashes, and applied Flyway checksums. Do not rewrite immutable historical change JSON to add attribution; use additive sidecars and V2 response metadata.
- Lock the dataset row when changing membership/archive state or applying financial mutations. Check the current member and membership incarnation under that lock; enforce last-admin protection atomically. Rejoining creates a fresh membership identity, so earlier queued work cannot acquire renewed authority. Reauthorize conflict resolution and dependent changes just like direct mutations.
- Invitations target an existing enabled account with verified email. A public authenticated relay resolves the exact email with pool-scoped Cognito `AdminGetUser`; it has no database credentials. It first obtains admin authorization from the private worker, then the worker checks authority again when inserting the invitation. Store only a digest of a random 32-byte token. Tokens expire after seven days, are revocable, and are consumed atomically only by the target subject. Recheck the inviting admin and tracker state at acceptance. Sharing is a copied link, not an automated email service.
- Links use a configured stage-specific HTTPS app origin and `/join#token=…`, with an explicit native-app link using the existing app scheme. The token remains outside financial snapshots, logs, analytics, and replay. Wrong-account and invalid links reveal no tracker contents. Account lookup failures are generic; no browsable account directory is introduced.
- Introduce tracker-scoped `/sync/v2` operations and tracker management endpoints. Existing V1 sync endpoints remain personal-only with unchanged wire shapes. V2 returns creator metadata separately and distinguishes authentication, membership, permissions, and archive failures. Preserve immutable submitted mutations and manual revision-based conflicts; push acknowledgments never advance pull cursors.
- Use a local tracker registry and independently encrypted dataset snapshots, outboxes, cursors, conflicts, write queues, and lifecycle generations. Keep the existing anonymous dataset as the private personal tracker during restart-safe schema migration. Back up before migration; publish the registry only after durable writes. Do not use obsolete `account:<stage>:<subject>` namespaces, which legacy cleanup resets. Introduction/recovery detection must recognize migrated data.
- Language, theme, analytics consent, and notice choices are device-local and survive switching/replacement. Base/selected currencies belong to the selected tracker. All five product routes use the selected tracker; filters, drafts, queries, and pending callbacks are tracker-scoped. Shared stores are inaccessible to a different signed-in subject or after sign-out, while durable work remains encrypted.
- Shared trackers support offline reads and financial edits from cached permissions. Sync enabled trackers sequentially on existing lifecycle/local-save/manual triggers. Server authorization is authoritative on reconnect; there is no claim that offline removal can be detected immediately. Archived trackers remain readable and reject financial writes until restored; permanent cloud deletion is deferred.
- When leave/removal becomes known, immediately hide the tracker and invalidate work. Clear fully synchronized caches. If unsynced work remains, quarantine the encrypted local data and keep it inaccessible until its owner explicitly confirms deletion of the tracker-local snapshots, backups, and outbox. Declining deletion never restores access. No automatic personal-copy recovery is provided.
- Foreground voice captures its target before recording and uses that same target for categories, save, retry, and edit. Shared voice supplies dataset and membership context; authorize before invoking providers. Voice remains expense-only. Personal voice continues to work independently of personal sync.
- Wear OS has an encrypted watch-local tracker selector independent of the phone's visible tracker. Protocol V2 captures tracker ID, shared membership identity, local target generation, and the recording-start calendar date. Carry immutable target metadata through encrypted queues, phone processing, receipts, and terminal acknowledgments. Process inactive targets without switching the UI. Legacy recordings/protocol V1 resolve only to their originating personal tracker. Never redirect a stale or unavailable target. Audio recovery remains outside financial sync and is not silently erased by financial cleanup.

## Consequences

Shared permissions can change while a device is offline, so rejected work remains visible as a generic pending-data deletion notice rather than being silently discarded. Membership and dataset generations add lifecycle checks to UI, background work, and sync. Additional server routes and a narrowly scoped Cognito relay preserve private PostgreSQL workers without adding NAT or broad directory permissions.

## Validation

Cover schema-8 migration/restart/recovery and unchanged submitted hashes; independent tracker caches/outboxes; server role and own-entry enforcement; concurrent last-admin checks; invitation identity/expiry/revocation/replay; archived writes; removal/quarantine/confirmed deletion/rejoin; legacy V1 isolation; metadata-only pulls; and target-pinned foreground/headless voice. Native checks include protocol compatibility, watch date preservation, delayed delivery, duplicate receipts, membership changes, and paired-device acceptance. Keep financial/identity/audio contents out of diagnostics and analytics. Release migrations before compatible backend handlers, then phone/web and watch clients through the existing staged deployment gates.
