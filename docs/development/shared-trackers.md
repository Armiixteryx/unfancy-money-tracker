# Shared tracker development and acceptance

[ADR 0024](../adr/0024-shared-family-trackers.md) defines roles, invitations, local isolation, and voice targeting. The personal sync runbook remains applicable to personal datasets.

## Release order

1. Build the migration package and validate Flyway history before applying forward migrations. Existing personal datasets and submitted mutation bodies must remain unchanged.
2. Release the membership-aware workers and authenticated tracker relay before the schema-9 client. Set CDK context `publicAppOriginDev` / `publicAppOriginProd`, or build-time environment `PUBLIC_APP_ORIGIN_DEV` / `PUBLIC_APP_ORIGIN_PROD`, to the stage's HTTPS app origin. The selected value becomes the relay's runtime `PUBLIC_APP_ORIGIN`. Synthesis can succeed without an origin; invitation creation then fails closed. The relay resolves existing verified Cognito identities; it does not create users or send invitations.
3. Release the client and protocol-2 phone/watch pair. Older clients and protocol-1 recordings remain personal-only.

Use the existing explicitly gated deployment workflow. An implementation request does not authorize a cloud release.

## Synthetic family acceptance

Use three temporary verified accounts with analytics disabled. Share invitation links manually. Do not include tokens, account identities, financial records, SQL parameters, or audio contents in diagnostics.

- Create a family tracker as the first account, invite a second account as admin and a third as member, and accept each link while signed into its intended account. A different account, an expired/revoked link, and a consumed link must fail.
- Confirm each account retains its personal tracker. Switch between personal and family data, restart offline, and confirm cached records and pending edits stay isolated.
- Add income and expenses as the member. Confirm authorship, own-record editing/deletion, and denial of edits to another author's records, budgets, categories, currencies, name, and membership. Repeat requests directly against the API to verify server enforcement.
- Promote/demote and remove members. Confirm concurrent actions cannot remove or demote the final admin. Archive the tracker, verify read-only behavior, then restore it.
- Queue an offline edit, remove its author from another account, and reconnect. Access must disappear when revocation is learned. Pending local work stays inaccessible until deletion is explicitly confirmed; declining deletion must never restore access.
- Choose a family tracker independently on Wear OS. Record an expense, change the phone's selection before delivery, and confirm the recording retains its original target and watch-local date. Repeat during account switch, archive, membership revocation/rejoin, and local reset. Failed encrypted audio must remain recoverable and must never reroute.
- Test personal sync upload/merge/replacement after the registry migration, including a changed canonical dataset ID. Confirm language, theme, analytics consent, and notices remain device-local.

Build and unit-test results do not establish interactive phone/watch acceptance. Record each observed outcome separately, including platform, build configuration, and any untested lifecycle.
